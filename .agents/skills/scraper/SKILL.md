# news-digest スクレイパー生成・修正代行手順

あなた（AIコーディングエージェント）は、このドキュメントに従ってユーザーと対話しながら
news-digestの「scraper方式」（RSS/Atomフィードを提供していないサイト向けの取得方式）の
スクレイパースクリプトを**生成（author）**または**修正（repair）**してください。

このドキュメントは特定のAI製品・ベンダーに依存しないプレーンな指示書です。
どのAIコーディングエージェントで読み込んでも同じ手順で実行できるようにしてください。

**このSkillの目標は、ユーザーに指摘される前に自分で不具合に気づき、自分で直すことです。**
下記「実データ突合せ」は生成・修正のたびに**必ず自発的に実行する**手順であり、
ユーザーから「古い」「件数が少ない」といった指摘を受けてから動く手順ではありません。
ユーザーへの確認が必要なのは、実配信先へのテスト送信の実行可否と、外部依存の採用可否
（下記参照）だけです。それ以外の正しさの検証は、Skill自身が完結させてください。

## このSkillの位置づけ（作業を始める前に必ず理解しておくこと）

- スクレイパーは `scrapers/{scraper_id}/scraper.py` に配置され、
  `fetch(options: dict, http: httpx.Client) -> list[dict]` という契約のみを守る
  疎結合設計です。`src/core/models.py` の `Article` など、news-digest本体のモジュールを
  直接importしてはいけません。これは、あるサイトのレイアウト崩れやスクレイパーの
  バグによる影響をそのサイトの取得失敗に限定し、本体のデータモデルやパイプライン
  全体に波及させないための設計です。
- `scrapers/` 配下は `scrapers/example-blog/`（テンプレート）を除き `.gitignore` 対象です。
  スクレイパーは本リポジトリをローカルにインストールした各利用者が対象サイトに
  合わせて個別にカスタマイズするものであり、リポジトリ本体で共有・レビューする
  成果物ではありません。したがって **生成・修正した `scrapers/{id}/` はコミットせず、
  ブランチ作成やPR作成も行わないこと。** ローカルファイルとして生成・修正し、
  契約チェックリストで自己検証した内容をユーザーに直接提示してください。
- `options` には `url`（フィード設定のURL）/ `feed_name`（フィード名）/
  `category`（カテゴリ）が渡される。通常は `options["url"]` のみ使えばよい。
- `published_at` は **ISO 8601形式の文字列（例: `"2026-07-31"`、
  `"2026-07-31T09:00:00+09:00"`）で返すこと。** `src/core/scraper_fetcher.py` が
  `datetime.fromisoformat()` でのベストエフォート変換を試み、成功した場合のみ
  `filters.max_age_days` による日付フィルタが有効になる。ISO 8601として解釈できない
  表記（`"July 31, 2026"` や `"2026年7月31日"` のような対象サイトの生表記のまま）を
  返すと、変換に失敗して `max_age_days` が無条件にスルーされ、何ヶ月も前の記事が
  延々と配信対象になり得る。対象サイトの表記がISO 8601でない場合は、
  `scraper.py` 側でISO形式に変換してから返すこと。

このSkillには2つのモードがあります。ユーザーの依頼内容に応じてどちらのモードかを
判断し、以下の該当する手順に従ってください。

## 生成（author）モード

**トリガー**: ユーザーがRSS/Atomを提供していない新しいサイトの対応を依頼したとき。

### 手順

1. ユーザーから以下を確認する。
   - 対象サイトの一覧ページのURL
   - スクレイパーid（未指定であればサイト名やドメインから kebab-case で提案する。
     例: `example.com/blog` → `example-blog`）
2. 対象ページのHTML構造を取得・把握する。実際に一覧ページを取得し、記事タイトル・
   URL・日付・要約に相当する要素がどのタグ・クラス名・属性で表現されているかを
   特定する。
3. `scrapers/{id}/scraper.py` を作成する。
   - `fetch(options: dict, http) -> list[dict]` 契約を実装する。
   - 標準ライブラリ（`re` / `html.unescape` 等）のみで完結させることを推奨する。
   - 参考実装として `scrapers/example-blog/scraper.py` を必ず参照すること
     （`<article>` 要素の繰り返しから `url`/`title`/`summary_source`/`published_at`
     を正規表現で抽出するスタイル）。
   - news-digest本体のモジュール（`src.core.models` 等）をimportしないこと。
   - **正規表現の文字クラスを、確認した1件のサンプルだけから広げすぎず/狭めすぎず
     設計すること。** 特にIDやラベルなど「サイトが値を生成している」箇所を
     `[a-z0-9-]+` のようなASCII限定パターンで決め打ちしない。日本語ローカライズ
     サイトでは日付・スラッグ等が非ASCII表記に変わることがある。可能なら
     取得した生レスポンス全体をgrepし、想定パターンに当てはまらない出現がないか
     確認してから正規表現を確定させる。
     > 実例（`devin-release-notes`、2026-08-05）: `id="april-3-2026"` という
     > ASCII表記のIDが、ある時点以降の新しい記事だけ `id="2026年7月31日"` という
     > 日本語の生日付表記に変わっていた。抽出の正規表現がASCII限定
     > (`[a-z0-9-]+`) だったため、新しい記事が静かに全部除外され、
     > 何ヶ月も前の記事しか取得できていないように見えていた。
4. `scrapers/{id}/sample.html` を作成する。対象ページの実際の構造を模した
   オフラインfixtureとし、ネットワークなしでテストできるようにする。
5. `scrapers/{id}/expected.json` を作成する。`sample.html` に対して `fetch()` を
   実行した場合に返るべき期待値を手動で検証して記載する
   （`scrapers/example-blog/expected.json` の形式に倣う）。
6. **下記「実データ突合せ」を実行し、対象サイトの実データに対して
   `fetch()` が漏れなく抽出できているか自分で検証する。** ここで不一致が
   見つかった場合はユーザーに提示する前に自分で原因を特定し修正すること。
7. 下記「契約チェックリスト」で自己検証する。
8. `config.yaml`（`config.example.yaml` ではなく実運用ファイル）の `feeds` に
   `source_type: scraper` + `scraper_id: {id}` のエントリを実際に追記する。
   カテゴリ等の値はユーザーに確認して埋める。このとき併せて「このフィードだけ
   個別の配信先（Slack/Google Chat）に配信したいですか？（任意・スキップ可。
   何も指定しなければ従来通りグローバルの `delivery:` 設定が使われます）」と
   尋ねてください。希望があれば、そのフィードのエントリに `delivery:`
   （`name` / `format`: `slack` または `google_chat` / `webhook_url_env` /
   `enabled`、既定true）を追記してください。希望がなければ何も追記せず、
   グローバルの `delivery:` 設定がそのまま適用されます。
9. テスト送信を行う（下記「テスト送信」を参照）。
10. `scrapers/{id}/` は `.gitignore` 対象のローカルファイルであり、コミットや
    PR作成は行わない旨をユーザーに案内する。

## 修正（repair）モード

**トリガー**: `uv run news-digest --db state/digest.db scrapers check` の結果、
対象scraper_idの `status` が `error` または `empty` になっている（壊れ検知）とき、
人（ユーザー）がこのSkillを起動する。

### 手順

1. 対象の `scraper_id` を特定する。`scrapers check` の出力、または
   `source_health` テーブルの `error` 列のメッセージから原因の当たりをつける。
   ユーザーからの「古い」「件数が少ない」といった指摘がトリガーの場合も、
   まずこのモードの手順として自分で切り分けを行う（下記「実データ突合せ」）。
2. 既存の `scrapers/{id}/scraper.py` / `sample.html` / `expected.json` を読み、
   現在の実装が前提としているHTML構造を把握する。
3. 下記「実データ突合せ」を実行し、対象サイトの現在の実データと
   現行の `scraper.py` の抽出結果を突き合わせて、何が変わったか
   （タグ構造・クラス名・属性・値の表記形式など）を自分で特定する。
4. `scrapers/{id}/scraper.py` のパース処理を新しい構造に合わせて修正する。
   `fetch(options, http) -> list[dict]` 契約・疎結合設計（本体モジュール非import）
   は維持すること。
5. `scrapers/{id}/sample.html` を新しい構造のfixtureに更新し、`expected.json` も
   新しい期待値に更新する。
6. 修正後、再度「実データ突合せ」を実行して不一致が解消したことを確認する。
7. 下記「契約チェックリスト」で自己検証する。
8. テスト送信を行う（下記「テスト送信」を参照）。
9. `scrapers/{id}/` は `.gitignore` 対象のローカルファイルであり、コミットや
   PR作成は行わない旨をユーザーに案内する。

## 実データ突合せ（両モード共通・必須・自発的に実行する）

生成・修正の完了条件は「`sample.html`固定fixtureに対して`fetch()`が正しく動く」
ことだけでは不十分です。**固定fixtureは一時点のスナップショットに過ぎず、
サイト側の表記変更を検出できません。** 必ず対象サイトの「今」の実データに対して
以下2つのチェックを**両方とも独立に**自分で実行し、ユーザーに見せる前に
不一致を潰しておくこと。片方が一致していても、もう片方は別の理由で
不一致になり得るため、どちらか一方で済ませないこと。

1. 対象ページを実際に取得し（`curl`や簡単なPythonスクリプトで可）、生の
   レスポンス本文をファイルに保存する。

2. **チェックA（総数の突合せ）**: 繰り返し単位の総出現数を、`scraper.py`の
   正規表現とは別の、より緩い基準（クラス名のみ等）で機械的に数える。
   （例: 対象が `<div class="update ... update-container" id="...">` の
   繰り返しなら `grep -c 'class="update[^"]*update-container"'` のように、
   IDやラベルの表記パターンに依存しない数え方をする。）この数と`fetch()`が
   返す件数を突き合わせる。
   - 注意: この方式には限界がある。抽出条件とカウント基準が同じ属性
     （例: どちらもクラス名基準）を使っている場合、`fetch()`内部の
     `continue`等による一部レコードの取りこぼしは件数が一致したまま
     見逃される。**件数が一致しても安心せず、必ずチェックBも行うこと。**
   - 不一致が見つかった場合は、まず不一致の原因を理解する。多くは
     抽出ロジックの見落とし（正規表現の文字クラスがASCII限定になっている、
     ページ内に表記形式が複数混在している＝移行途中で古い記事と新しい記事の
     ID形式が違う、タグ構造の前提が一部の記事だけ変わっている、等）だが、
     ページ末尾の「すべて見る」リンクや隠し要素・テンプレート内の重複など、
     **除外して正しい場合もある**。不一致=即バグと決めつけず、原因を
     特定してから対処する。

3. **チェックB（先頭要素の突合せ、総数一致でも必ず実行）**: `fetch()`の
   戻り値の先頭（最新扱いの記事）が、生データ内で実際に最初に出現する
   記事と一致するかを日付・タイトルで直接確認する。件数が一致していても、
   「新しい記事が1件漏れて、代わりに末尾のノイズを1件多く拾った」ような
   相殺パターンはチェックAだけでは検出できない。このチェックが、
   「最新記事だけ静かに落ちる」系の不具合を最も確実に検出する。

4. チェックA・Bを両方クリアして初めて「取得結果が正しい」とみなせる。
   ここまでで生データそのものに欲しい情報が存在しないと確認できた場合に
   限り、ネットワーク経路・CDNキャッシュ・JSレンダリング等の外部要因を
   疑ってよい。その場合も、Playwright等の新規ツールを試す前に、まず
   別の取得手段（`curl`、別のUser-Agent等）で手順1からやり直し、原因を
   切り分けてから次の対応（ユーザーへの相談を含む）を検討する。

## 外部依存の追加について（両モード共通）

調査・原因切り分けの過程で、外部サービス（レンダリングプロキシ等）や
新規パッケージ（Playwright等）を一時的に使うのは問題ない。ただし
**それをそのまま最終実装（`scraper.py`本体）に採用する前に、必ずユーザーに
確認すること。** 検証用の手段と最終成果物は明確に分けて扱う。ユーザーの
確認なしに `scraper.py` の取得方式を外部サービス経由に切り替えたり、
`pyproject.toml` に新規依存を追加したりしないこと。

## テスト送信（両モード共通）

`sample.html` に対する `fetch()` の自己検証はオフラインの契約確認に過ぎず、
対象サイトへの実際のアクセス・要約・配信までは検証していない。生成・修正の
最後に、実際のパイプラインを1回走らせて疎通を確認すること。

1. **実行前に必ずユーザーに確認する。** `uv run news-digest --db state/digest.db run`
   は `config.yaml` の `delivery` に設定された実際の配信先（Slack/Google Chat等の
   webhook）に本番配信される。テスト目的でも実際のチャンネルに通知が届くことを
   ユーザーに伝え、実行してよいか確認してから進める。
2. 承認を得たら `uv run news-digest --db state/digest.db run` を実行する
   （このコマンドはconfig.yamlの全フィードを対象に1回分のバッチを実行する。
   対象スクレイパーのみを分離実行する手段は現状ないため、他フィードの新着も
   同時に配信される点をユーザーに伝えておく）。
   **注意: `--db state/digest.db`（本番の状態DB）を使うと、配信済み記事に
   `delivered_at` が記録され、以後の`run`では同じ記事が「配信済み」として
   除外される。** 同じセッション内で複数回テスト送信を行うと、2回目以降が
   `article_count=0` になり「新着0件＝バグ」と誤診しやすい。原因調査中に
   複数回テスト送信する可能性がある場合は、使い捨ての別DBパス
   （例 `--db /tmp/scraper-test.db`）を使うか、この重複排除の挙動をあらかじめ
   ユーザーに伝えておくこと。
3. `uv run news-digest --db state/digest.db scrapers check` で対象 `scraper_id` の
   `status` が `ok` であることを確認する。`error`/`empty` の場合は原因を調査し、
   必要であれば修正（repair）モードの手順に戻る。
4. 配信先に実際に通知が届いたか（記事が縮退配信ではなく要約付きで届いているか
   等）をユーザーに確認してもらう。

## 契約チェックリスト（両モード共通）

生成・修正のたびに、以下を必ず自己チェックしてください。

- [ ] `fetch(options: dict, http) -> list[dict]` のシグネチャ通りか
- [ ] `src/core/models.py` 等news-digest本体のモジュールをimportしていないか
- [ ] 戻り値の各要素は `url` と `title` が非空か（欠落・空文字は契約違反として
      取得失敗扱いになる）
- [ ] `sample.html` に対して実際に `fetch()` 相当の処理を動かし、`expected.json`
      と一致することを手動で確認したか（可能であれば `tests/test_scraper_fetcher.py`
      のテストパターンを参考に、簡単なPythonスクリプトで検証することを推奨する）
- [ ] 「実データ突合せ」を実行したか（ユーザーからの指摘を待たず自発的に）。
      チェックA（生データの総出現数と`fetch()`の抽出件数の一致）と
      チェックB（`fetch()`の戻り値の先頭が生データの実際の最初の出現と
      一致するか）の**両方**を確認したか（件数が一致していてもチェックBを
      省略していないか）
- [ ] `published_at` をISO 8601形式（`YYYY-MM-DD`等）で返しているか。対象
      サイトの生表記のまま返していないか
- [ ] 外部サービス・新規依存を最終実装に使う場合、ユーザーに確認を取ったか
      （検証目的の一時利用にとどめていないか）
- [ ] `config.yaml`（実運用ファイル）にfeedエントリを実際に追記したか
- [ ] 実配信先へ本番配信されることをユーザーに確認したうえでテスト送信を行い、
      `scrapers check` の `status` が `ok` であることを確認したか
- [ ] `scrapers/{id}/` はコミット・PR作成をせず、ローカルファイルとしてユーザーに
      直接提示したか
